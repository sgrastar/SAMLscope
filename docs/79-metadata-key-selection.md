## Runner receipt reader (originals required)

`MetadataSignatureVerificationEvidenceFile` does not trust receipt strings: the Runner reads and verifies referenced originals. The receipt's `configurationReadBack`, `restorationReadBack`, and each negative control's `rejectionReference` point to `tx_` transcript entries. The Runner reads actual bytes through `content.readDecodedSaml`, checks the declared SHA-256, and then examines semantics. The binding covers Run, `campaignId`, `targetEntityId` (matching the target metadata entityID), original fixtures, requests/responses, and configuration changes/restoration. Configuration read-back requires evidence that the product read the out-of-band anchor (a fingerprint of the anchor-certificate bytes) and that it differs from the fixture's embedded KeyInfo certificate. Restoration read-back requires identical configuration bytes before and after the change. Negative controls require the product's own rejection Response (top-level Requester/Responder), correlated to the target request. Thus `restored:true`, a `source` name, a timestamp string, or a bare hash alone is insufficient. Native-rejection receipt paths for MD05.am/an are gated by the same prerequisites.

The above describes the boundary when the v3 reader was completed. At that time, an adapter recording product-side originals had not been implemented, so actual Runs failed closed and remained unverified. The current SimpleSAMLphp path is connected through the v4 native adapter and adoption verification described below. This adoption alone does not resolve deficiencies in other adapters or prerequisite evidence. Approved configuration failure semantics (such as VIOLATED for missing `normative_capability`) are not gated again.
